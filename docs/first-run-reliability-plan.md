# Reflow: simpler code and reliable first-run setup

22 October 2026. Planning document for Windows, macOS, and Linux.

The outcome is a packaged app that a new user can install, configure, and use without developer tools, terminal commands, or AI-assisted repairs. The first successful dictation proves that the selected microphone, shortcut, runtime, model, and text insertion work together. Optional local writing models come afterward.

This plan applies Ponytail **5.3.2, Full**: reuse existing components and platform facilities, fix shared causes once, remove duplication, and retain validation, recovery, privacy, accessibility, and hardware checks. The release was verified against the [upstream releases](https://github.com/DietrichGebert/ponytail/releases/tag/v5.3.2); the [main skill](https://github.com/DietrichGebert/ponytail/blob/v5.3.2/skills/ponytail/SKILL.md) and [audit skill](https://github.com/DietrichGebert/ponytail/blob/v5.3.2/skills/ponytail-audit/SKILL.md) were read for this review.

The supported load is one person's desktop, with simultaneous hotkeys, UI actions, background installations, file transcription, and an optional phone/API client. Concurrency within that desktop is the primary race-condition risk.

## The first-run experience

Keep the established Reflow interface and its calm, keyboard-accessible behavior. Present one primary action per stage; show technical details only when they help recovery.

1. **Choose and test the microphone.** Ask for the relevant OS permission, list real input devices, show a live level, and capture a short sample. Distinguish unavailable device, permission denial, silence, clipping, and capture failure. Changing the device invalidates its test. If no microphone works, offer explicit setup deferral rather than a success badge.
2. **Choose and test shortcut keys.** Save/register the shortcut, resolve collisions, and confirm that the OS delivers its press/release events without needing an ASR model. Explain hold/toggle behavior, including Wayland portal limitations. If a global shortcut is unavailable, offer Record-button mode explicitly. Check automatic-paste permissions separately.
3. **Check hardware and propose a speech configuration.** Detect OS/version, architecture, CPU instructions, available RAM, GPU/driver capability, VRAM, and storage on the actual data/cache volumes. Include the user's recognition language in model suitability. Show a recommended compatible model and its dependency/download/storage budget; permit an informed override that still passes admission checks.
4. **Install and verify speech dependencies.** Download only the runtime profile required by the proposed model. Show the selected CPU/GPU path, real phase/byte progress, cancellation, and actionable recovery. Do not mark dependencies ready until imports, exact package versions, CPU execution, and any selected GPU execution pass.
5. **Download and verify the ASR model.** Keep model weights separate from dependencies. Verify the pinned artifacts, load the model on the reported device, and expose a clear Retry/Repair path. Changing to another engine reruns dependency planning and explains any additional setup; never install every engine preemptively.
6. **Complete a real dictation.** Test microphone-to-text recognition, then use the actual shortcut/Record fallback to insert text into a controlled field. Offer an external editor/terminal check and clearly report clipboard-only mode if OS insertion is unavailable. Typing into a field must not count as proof that dictation inserted text. Finish records the exact tested configuration and any accepted limitations.

After first success, offer **Optional writing cleanup**. Its sequence is: hardware/memory budget → install and verify the writing runtime → download selected LLM → verify/load → run a short cleanup check. Declining or failing this step leaves ordinary dictation working.

Users can leave setup and resume. The Home page shows the next unfinished requirement. A deferred setup never displays “ready”; repaired hardware or a changed model invalidates only the affected checks.

## Packaging decision

Use a normal desktop installer plus downloadable, versioned runtime packs. Keep large ASR/LLM weights out of the base installer and download only what the user chooses.

- The installer includes the app, speech scripts, manifests/locks, licenses, and required desktop assets. Packaged users need no Node.js, Rust, system Python, CUDA toolkit, or compiler.
- Build each supported speech pack from the existing target/engine/device lock. Include a pinned standalone Python distribution, a complete binary wheelhouse, required redistributable libraries, licenses, and a verified artifact manifest. Install wheels locally with fixed hashes and no dependency resolution or source builds.
- Reuse the current generation installer: create the environment at its permanent generation path, verify it, then promote the active pointer. **Do not archive and relocate a populated virtual environment**; its scripts and interpreter links can contain absolute paths.
- Test every distributed pack on its native target. Cache complete verified artifacts for retries. Keep the incumbent generation through a failed repair; reclaim superseded generations only when no running job references them.
- Ship matching, pinned writing-runtime packs separately. Reuse an already-verified compatible runtime, including when native ASR shares it; prevent replacement/removal while either ASR or writing owns it.
- Keep hardware drivers under OS/user control. Auto selects acceleration only after verification; forced GPU reports an actionable failure when unavailable. CPU fallback must still fit RAM and support the requested language.
- Sign Windows installers and macOS app/runtime executables; notarize macOS releases. Verify WebView/runtime prerequisites, quarantine behavior, Linux desktop-library dependencies, and executable permissions from the installed artifact.

This reuses the existing installer and locks while moving upstream package assembly into release preparation. Runtime-pack implementation and licensing checks are required work, not functionality already present.

Initial artifact targets: Windows x64, Linux x64, macOS Apple Silicon, and macOS Intel. Intel Mac currently has a Zipformer-only managed lock, which is English-only; do not claim multilingual parity there until an appropriate engine is added and tested. Linux ARM64 and additional acceleration backends require their own acceptance evidence before being advertised. Current AMD/MPS capability must be described according to measured support, not GPU detection alone.

## Backend invariants to enforce

- **One owner per mutable resource.** Two windows requesting the same setup join the same job. Conflicting install/load/remove operations queue or return a recoverable busy result. Retain existing session ownership and define one lock order for session, settings, runtime, and model operations; avoid holding a blocking mutex across an async wait.
- **An attempt keeps its configuration.** Capture target, engine, device, precision, model revision, language constraints, and dependency digest before work starts. A late settings change creates a new desired configuration rather than relabeling the active job. Cancellation and progress carry the attempt ID; old events cannot finish or cancel a replacement.
- **Snapshots survive missed events.** Extend existing backend status with current phase, terminal result/error, attempt/configuration identity, and latest progress. UI subscriptions render snapshots and reconnect safely. Persist only restart-relevant checkpoints; do not add a second job database.
- **Ready means usable.** Distinguish downloaded, verified, runtime healthy, model loaded, recognition passed, and insertion mode. Recheck live RAM/VRAM before load and CPU fallback. File presence or an old receipt alone cannot establish readiness.
- **Promotion preserves the working copy.** Verify and flush staged artifacts before activation. Test active-pointer replacement on Windows and crash durability on each filesystem. Deleting an incumbent before replacement is successfully committed is forbidden. Failed/cancelled jobs never emit success.
- **Cancel means owned work stops.** Stop child process trees and network activity, release resources, preserve reusable bytes, and publish one terminal result. A detached UI listener alone is not cancellation. Restart distinguishes a resumable download from an abandoned, unverified generation.
- **Downloads stay bounded and private.** Preserve HTTPS/host restrictions, hashes, archive-path/symlink protections, and offline policy during transfers. Use finite connection/read-idle waits and retries that respect server throttling. Validate resumed ranges, reset safely when Range is ignored, and handle unknown lengths without misleading percentages.
- **Data survives failures.** Settings and migration recovery preserve original bytes; transcript/segment writes stay transactional; optional retention failures do not lose transcripts. Cancellation, late completion, or an authorization change cannot insert stale text into another session or application.
- **Trust boundaries remain validated.** Check Tauri/API options, model IDs, file paths, imports, sample rates, audio sizes, tokens, permissions, listener scope, and revocation. Keep API requests bounded; exercise phone/API ownership alongside keyboard and file jobs. Avoid secrets or private audio/transcripts in diagnostic bundles.

## Final verification and release evidence

Run the existing full gates for the final tree: `npm run check`, `npm run build`, locked Rust tests and all-target Clippy, Rust formatting, Python runtime/protocol/dependency-policy tests in the intended managed environment, packaging/release tests, and current dependency advisory scans. Check opt-in tests individually; an ignored hardware test is not a pass. Existing distribution tests include synthetic staging/checksum examples, so real installer/transfer fault tests must exercise production code as well.

For each supported installer/runtime-pack combination, retain the source-tree identity, artifact hashes/signatures, OS/architecture, hardware/driver details, selected lock/profile, actual loaded device, test results, setup/download timing, peak RAM/VRAM/storage, and known limitations. Use a new OS user/profile or restored clean image without system Python, inherited virtual environments, development tools, model caches, or prior app data.

The release journey is: install → deny/retry relevant permissions → microphone test → shortcut test → hardware plan → dependency installation → weight download → recognition → external insertion or explicitly accepted clipboard fallback → quit/restart → repeat offline → optionally set up writing runtime and LLM → exercise a failed repair and recover. Repeat on Windows, macOS, Linux X11, and supported Wayland desktops; CPU and advertised accelerated profiles require separate evidence.

Keep macOS preview until native input, insertion, startup, signing/quarantine, and runtime-pack acceptance pass. Protect existing phone/Android behavior with its current tests; this desktop plan does not expand Android scope. Add the acceptance gate to the existing release workflow so a successful build/provenance check alone cannot label an untested platform stable. No release is published as part of this planning task.

Success is an evidence-backed support matrix with no unresolved release-blocking defects, recoverable tested failures, and a smaller shared implementation. A finite suite cannot prove that every possible machine and edge case is bug-free; record unsupported and unverified combinations instead of promising universal success.

## Review limits

This was a targeted planning review of first-run setup, runtime/model installation, hardware selection, session ownership, API boundaries, packaging, and the existing audit evidence. It was not a line-by-line review of the whole application. No fresh multi-GB runtime/model setup, microphone recognition, external insertion, physical Windows/macOS test, complete test-suite rerun, performance measurement, or new security advisory scan was performed for this plan.
